# XCOD-239: upstream OpenCode v2 — feature map, estimate and recommendation

**Status:** analysis, awaiting PO decision · **Date:** 2026-10-13 · **Author:** spike (agent), for
Petar Minev (product owner) · **Type:** research spike, no product code changed
**Related:** XCOD-16 (merge, never rebase), XCOD-118 (weekly upstream sync), XCOD-174 / XCOD-221
(no upstream services), XCOD-179 (6-month security support), XCOD-207, XCOD-227, XCOD-238

> **Analysis, not a commitment.** Every estimate below is a range from reading code, not from doing
> the port. Treat the person-day figures as low-to-medium confidence. Nothing here schedules work;
> the decisions are listed at the end.

## Recommendation

**Stay on v1 for now and don't merge upstream `dev`. Track upstream's `v1` branch and `v1.x`
tags (option B, already in progress). Plan the move to v2 as a re-fork on a separate branch
with its own pre-release channel, not as a merge, and start it only when one of the named
triggers fires (below).**

Why:

1. **v2 is a rewrite, not a release.** Upstream promoted v2 to `dev` on 2026-10-10
   (`5caf1f9f6f`, "chore: promote v2 to dev", 4,387 commits on the v2 side). `packages/opencode`,
   which holds most of Lunos, **no longer exists** in v2. Between the last common point
   (`907b3bc518`, 2026-10-02) and upstream `dev` (`bcf23b6775`, 2026-10-12), 8,452 files
   changed. Of the files Lunos touched, **all 418 under `packages/opencode` are gone**, and so are
   91 of the 95 `packages/app` files Lunos modified, and 37 of the 38 files Lunos added under
   `packages/tui`.
2. **The evidence is already in.**
   - PR #190, the automated merge of upstream `dev` at `bcf23b6775`, is a draft with **about
     1,150 conflicting files**.
   - The parallel v1 sync merges `v1.19.0` with **44 conflicts** (`upstream-sync/v1.19.0` @
     `0496cbc317`).
3. **Upstream is still shipping v1.**
   - It created a `v1` branch and publishes 1.x from it (`9b14c13476`) and tagged `v1.19.0` on
     2026-10-11.
   - On 2026-10-12 it was still working on v1 update isolation (branch `v1-update-isolation`,
     `9e84409de0` "keep OpenCode 1 updates on 1.x").
   - Nothing in the tree announces an end-of-life date.
4. **Porting costs 117–183 person-days, or 147–228 with contingency.** For one person that is
   about **7–11 months**. It would also reopen EU guarantees Lunos has already closed:
   - v2 brings back a keyless `apiKey: "public"` path to opencode.ai, which XCOD-221 removed.
   - Its update check goes to `opencode.ai/update/api`.
   - Its default model catalogue is `models.opencode.ai`.
   - Its MCP OAuth client identity is an opencode.ai URL.
5. **Staying on v1 is reversible; migrating may not be.** v2 opens the same `opencode.db` and
   applies 12 database migrations that Lunos v1 doesn't have, including `DROP TABLE workspace`.
   Whether a v1 binary still starts afterwards is untested. Staying keeps every option open, and the
   cost of waiting is bounded and measurable.

**Do now (small):**

- Land the sync retarget to upstream `v1` tags.
- Close PR #190 without merging.
- Add the **v2 regression guards** listed under Risks to the weekly sync review.
- Re-evaluate on the trigger dates below.

## Outbound services and defaults v2 adds

`opencode.ai` mention in `packages/*/src` outside a short allowlist.

## How long upstream keeps v1

- **No announcement in the tree.** `migrate-v1.mdx` says only "keep your V1 setup until you have
  confirmed the V2 behavior you need". `README.md` still installs `opencode-ai` (v1).
- **What the code shows:**
  - `v1` branch created 2026-10-10. 1.x is published from it (`9b14c13476`), and deploys from it
    are removed (`7062121a19`).
  - `upgrade --major` (`c28b6a0a3b`) and a v2-style `/update` dialog (`9c97b807d0`) push v1 users
    towards v2.
  - `v1-update-isolation` (`9e84409de0`, 2026-10-12) keeps v1 installs on 1.x via the update
    service. That is maintenance work, not abandonment.
- **Cadence:**
  - v1: 1.18.28 (09-04), 1.18.30 (09-09), 1.18.33 (09-28), 1.18.34 (09-30), 1.18.35 (10-06),
    1.19.0 (10-11). Roughly one or two a week.
  - v2: 2.0.0 (09-11) to 2.0.27 (10-12), 27 releases in a month.
  - Since the promote, the v1 branch carries 8 commits, mostly release plumbing and nudges to v2.
- **Reading:** v1 is in **maintenance mode with an active off-ramp**. Expect the v1 cadence to fall
  to security and provider fixes within weeks, with no published end date. The trigger below is
  what turns that into a decision.

## Plan

**Shape of the migration, when it happens: a parallel re-fork, delivered in waves. Not a
big-bang merge, and not an incremental merge into `dev`.** v2 can't be merged into `dev` piece by
piece; PR #190 shows the whole tree conflicts.

1. **Now (this sprint, small):**
   - Retarget `upstream-sync.yml` to upstream `v1` tags.
   - Close PR #190.
   - Add a weekly "v2 watch" line to the sync report: upstream v1 commits/tags in the last 14 days,
     and any `GHSA`/security fix that lands only in v2.
   - Keep XCOD-179's promise: every Lunos release gets 6 months of security fixes, so v1.18.46
     needs fixes until 2027-04-09.
2. **Groundwork while waiting (optional, ~5–8 pd, makes the port cheaper):**
   - Move residency, audit, policy and memory behind narrow modules shaped like v2 plugin domains
     (catalog transform, `aisdk` hook, tool hooks, event subscriber).
   - Keep new feature work out of `packages/opencode/src/session/prompt.ts` where possible.
3. **When a trigger fires:**
   - Branch `lunos-v2` from an upstream v2 **tag**, not `dev`.
   - **Wave 1** (34–53 pd, about 7–11 weeks), the compliance core: foundation, outbound hardening, residency,
     audit, managed policy and offline mode. Ship it as `lunos-ai@next` / a "Lunos 2 preview",
     using a separate data file so it can't touch `opencode.db`. v2 already supports one: a
     non-stable `OPENCODE_CHANNEL` uses `opencode-<channel>.db` (`packages/cli/src/database-path.ts`).
   - **Wave 2:** settings, sessions, models, agents, external agents, sandbox.
   - **Wave 3:** memory, marketplace, cloud, eval, docs.
   - Cut over the `latest` dist-tag only when a parity checklist built from the feature map is
     green and the egress check passes on the published binary.
4. **Rollback:**
   - Staying on v1 is trivially reversible.
   - For the re-fork, the v1 line stays publishable from a `v1` branch for the 6-month support
     window.
   - Lunos 2 must back up `opencode.db` before migrating, or use its own data directory. v2's 12
     extra migrations alter the shared file in place, and nobody has tested whether v1 still starts
     on it afterwards.
   - Switching `latest` back to 1.x is an npm dist-tag change.

### Triggers: start the re-fork when any one is true

- Upstream publishes an end-of-life or end-of-support date for OpenCode 1.
- **No upstream `v1.*` tag for 30 days.** The last one was v1.19.0 on 2026-10-11, so the first
  possible trigger date is 2026-11-10.
- A security fix (GHSA/CVE) or a provider-breaking fix (e.g. a model API change) lands upstream in
  v2 only, and backporting it to Lunos v1 takes more than 2 person-days.
- A paying pilot needs a v2-only capability, such as the remote service or the v2 plugin API.

Regardless of triggers, **re-run this spike on 2026-11-24** against the then-current upstream
tag. By then the v1 cadence and v2's stability will be visible.

## Risks

- **The weekly sync pulls v2 on Monday 2026-10-19.** `upstream-sync.yml` still defaults
  `upstream_ref` to `dev`. Until the retarget lands, the Monday 05:00 UTC run opens another
  ~1,150-conflict PR. A hurried
  merge of it would silently swap the product.
- **Upstream merges can reintroduce upstream services into v1 too.** The v1.19.0 merge brought
  `upgrade --major`, which installs upstream OpenCode 2 from opencode.ai. The parallel resolution
  rejected it; keep the allowlist test strict.
- **v2 regressions for Lunos users, whenever the move happens:**
  - LSP is accepted but not run.
  - `tui.json` becomes `cli.json`.
  - The permissions shape changes.
  - v1 plugins stop working, which kills the plugin half of the marketplace.
  - Keyless Zen comes back.
  - `models.opencode.ai` becomes the default catalogue.
- **A shared data directory, today.** Lunos and upstream both use `~/.local/share/opencode` and
  `opencode.db` (`packages/core/src/global.ts:10`). A user who also installs **upstream OpenCode
  2** will have upstream's 12 extra migrations and `V1Migration.run()` applied to Lunos's database,
  whatever Lunos decides. Worth a known-issue line and, eventually, a Lunos-owned data directory.
- **Compliance keys fail open on v2.** v2 ignores unknown config keys with a warning
  (`migrate-v1.mdx`). Unless `residency`, `audit`, `sandbox`, `cloud`, `external`, `agent_import`,
  `recommended` and the lock keys are registered in `packages/schema/src/config.ts` and fail closed, a
  v2-based build would accept an EU-only policy file and quietly not enforce it.
- **Moving target.** v2 ships about daily and is still changing core contracts (Effect upgrades,
  policy, event stream). Porting against `dev` would chase churn; port against tags.
- **Drift cost while waiting.** Every Lunos feature built on v1 adds to the port; memory alone is
  ~10.6k lines. Waiting is only cheap if new work stays modular (Plan step 2).
- **Security backports after v1 goes quiet** fall on Lunos, and XCOD-179 has published a 6-month
  support promise.
