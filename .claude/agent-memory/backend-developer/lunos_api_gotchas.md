Task 1 scaffolded `Lunos.Api` (Lunos.Api.sln, Lunos.Api/, Lunos.Api.Tests/) at repo root. Later tasks (health/contact endpoints, logging, etc.) build on it. Four gotchas found during that scaffold that will resurface:

1. **`dotnet new sln` on this machine's .NET 10 SDK (10.0.103) defaults to the new `.slnx` XML format**, not `.sln`. If a task needs to recreate/touch the solution file, pass `-f sln` explicitly or you'll get a `Lunos.Api.slnx` instead of `Lunos.Api.sln`.

2. **`WebApplicationFactory<Program>.WithWebHostBuilder(...).UseEnvironment(...)` needs `using Microsoft.AspNetCore.Hosting;`** in the test file. `ImplicitUsings` does not pull this in, and it's easy to confuse with the different `IHostBuilder.UseEnvironment` overload in `Microsoft.Extensions.Hosting` (wrong namespace, same method name, does not resolve for `IWebHostBuilder`).

3. **SQLite does not create missing parent directories.** The dev connection string is `Data Source=./data/marketplace.dev.db`; on a fresh checkout `./data/` doesn't exist and `db.Database.Migrate()` throws `SqliteException: SQLite Error 14: 'unable to open database file'`. `Program.cs` now does `Directory.CreateDirectory` (via `SqliteConnectionStringBuilder(connectionString).DataSource`) before migrating, guarded the same way as the migration itself (skipped under `Testing`). Same risk applies to the Production path `D:\lunos-data\marketplace.db` if that directory isn't pre-provisioned.

4. **This repo's git config treats paths case-insensitively** (macOS default). A `.gitignore` pattern like `Lunos.Api/**/data/` will also silently match `Lunos.Api/Lunos.Api/Data/` (the `Lunos.Api.Data` **source** namespace folder with `LunosDbContext.cs` and EF migrations) and `git add` will exclude those files without any error. Always scope ignore patterns by extension (`data/*.db`) rather than bare directory name when the name could collide with a C# namespace folder, and always run `git add -n <paths>` as a dry-run before the real `git add` on this project to catch this class of bug.

5. **Verifying a `WithWebHostBuilder` + `RemoveAll<DbContextOptions<T>>()` DbContext override actually took effect**: under the `Testing` environment, `Program.cs`'s own automatic `db.Database.Migrate()` is skipped (see gotcha 3's guard), so the *only* thing that calls `Migrate()` in a test that swaps in an in-memory SQLite connection is the test fixture's own constructor. That makes it a clean discriminator: `rm` any stray dev `.db` file under `<TestProject>/bin/Debug/net10.0/data/`, run only the target test class via `--filter`, then check whether the dev `.db` file reappeared. If it didn't, the override really redirected `LunosDbContext` to the in-memory connection — if it did, the override silently failed and the test migrated/ran against the real dev SQLite file instead. Confirmed working this way in Task 2's `HealthEndpointTests`. Note `CorsPolicyTests` (Task 1) legitimately creates this same stray file (it runs under `Development` on purpose), so always re-`rm` and re-run with a narrow `--filter` rather than the full suite when using this check.

6. **A bare `Assert.NotEqual(HttpStatusCode.OK, ...)` does not verify a "must return a specific non-200 status" AC** — it also passes if the handler throws and the global exception handler returns 500 by accident. When a brief's AC says "returns a non-200 status" as a deliberate behavior (not "anything but 200 is fine"), assert the exact expected status code (e.g. 503) plus that the forbidden 200-shaped body isn't present, not just inequality with 200.

7. **Nullable DTO properties on a minimal-API request body are NOT enforced as required at runtime, and a test claiming to guard "missing field" rejection may pass for the wrong reason.** Task 3's brief made `ContactRequestDto`'s `Email`/`Message` nullable specifically so a missing/null field wouldn't trip ASP.NET Core's own `ProblemDetails` 400 before the app's validator runs. Verified empirically: temporarily made them non-nullable, reran the "empty body returns validation_error envelope" test — it still passed identically. Minimal APIs don't run model-state/required validation on JSON body binding unless `AddValidation()` (.NET 10 opt-in) is wired up, which this project doesn't do. So a test posting `{}` and asserting the `validation_error` shape passes regardless of DTO nullability — it documents intent but doesn't discriminate the regression it's named after. If nullability enforcement ever becomes load-bearing, it needs an explicit test that would fail without the nullable design (e.g., asserting binding-time behavior directly), not just the end-to-end 400-shape check.

8. **Typed-DTO round-trip tests (`PostAsJsonAsync`/`ReadFromJsonAsync`) don't pin wire casing.** `System.Text.Json` defaults to case-insensitive property matching on both serialize and deserialize helpers, so a test built entirely on typed DTOs would pass even if the server emitted PascalCase JSON — despite a brief calling exact camelCase field names load-bearing for a frontend consumer. When the wire shape itself is the contract (not just the C# shape), add at least one test using raw `StringContent`/`ReadAsStringAsync` with literal lowercase JSON keys.

**Why this matters**: gotchas 2-4 and 7-8 are not visible from reading the task brief's code samples — they only show up when you actually run `dotnet test`/`git add`, or deliberately try to break an assumption the test claims to guard. Re-verify with a real test run, a `git add -n` dry-run, and (for "this test guards X" claims) an actual attempt to make X false and see if the test still passes.
