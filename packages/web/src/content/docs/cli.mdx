The Lunos CLI by default starts the [TUI](/docs/tui) when run without any arguments.

```bash
opencode
```

But it also accepts commands as documented on this page. This allows you to interact with Lunos programmatically.

```bash
opencode run "Explain how closures work in JavaScript"
```

---


### agent

Manage agents for Lunos.

```bash
opencode agent [command]
```

---

#### create

Create a new agent with custom configuration.

```bash
opencode agent create
```

This command will guide you through creating a new agent with a custom system prompt and permission configuration. Anything you don't allow is denied in the generated agent's frontmatter.

#### Flags

| Flag                                        | Short | Description                                                                                                                                                                                                                |
| ------------------------------------------- | ----- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| <nobr><code>{"--path"}</code></nobr>        |       | Directory to write the agent file to (defaults to global or `.opencode/agent` based on the prompt)                                                                                                                         |
| <nobr><code>{"--description"}</code></nobr> |       | What the agent should do                                                                                                                                                                                                   |
| <nobr><code>{"--mode"}</code></nobr>        |       | Agent mode: `all`, `primary`, or `subagent`                                                                                                                                                                                |
| <nobr><code>{"--permissions"}</code></nobr> |       | Comma-separated list of permissions to allow (default: all). Available: `bash`, `read`, `edit`, `glob`, `grep`, `webfetch`, `task`, `todowrite`, `websearch`, `lsp`, `skill`. Anything omitted is denied. Alias: `--tools` |
| <nobr><code>{"--model"}</code></nobr>       | `-m`  | Model to use, in `provider/model` format                                                                                                                                                                                   |

Passing all of `--path`, `--description`, `--mode`, and `--permissions` runs the command non-interactively.

### attach

Attach a terminal to an already running Lunos backend server started via `serve` or `web` commands.

```bash
opencode attach [url]
```

This allows using the TUI with a remote Lunos backend. For example:

```bash
# Start the backend server for web/mobile access
opencode web --port 4096 --hostname 0.0.0.0

# In another terminal, attach the TUI to the running backend
opencode attach http://10.20.30.40:4096
```

#### Flags

| Flag                                     | Short | Description                                                                |
| ---------------------------------------- | ----- | -------------------------------------------------------------------------- |
| <nobr><code>{"--dir"}</code></nobr>      |       | Working directory to start TUI in                                          |
| <nobr><code>{"--continue"}</code></nobr> | `-c`  | Continue the last session                                                  |

### auth

Command to manage credentials and login for providers.

```bash
opencode auth [command]
```

---

#### login

Lunos is powered by the provider list at [Models.dev](https://models.dev), so you can use `opencode auth login` to configure API keys for any provider you'd like to use. This is stored in `~/.local/share/opencode/auth.json`.

```bash
opencode auth login
```

When Lunos starts up it loads the providers from the credentials file. And if there are any keys defined in your environments or a `.env` file in your project.

##### Flags

| Flag                                     | Short | Description                                          |
| ---------------------------------------- | ----- | ---------------------------------------------------- |
| <nobr><code>{"--provider"}</code></nobr> | `-p`  | Provider ID or name to log in to                     |
| <nobr><code>{"--method"}</code></nobr>   | `-m`  | Login method label to use, skipping method selection |

---

#### list

Lists all the authenticated providers as stored in the credentials file.

```bash
opencode auth list
```

Or the short version.

```bash
opencode auth ls
```

---

#### logout

Logs you out of a provider by clearing it from the credentials file.

```bash
opencode auth logout
```

### project

Named projects: several repositories or directories counted as one, for example "Axsion web" for
`axsion-web`, `axsion-api` and `infra`. A repository is a project of its own without any of this.
Named projects are kept on this computer only. A session counts in the project of its working
directory (the deepest folder wins), a subagent's in its parent's; `/sessions` can move one.

```bash
lunos project create "Axsion web" ../axsion-web ../axsion-api
lunos project list
lunos project add "Axsion web" ../infra
lunos project remove "Axsion web" ../axsion-api
lunos project rename "Axsion web" "Axsion"
lunos project archive "Axsion"
```

A project is named by its name or its id (`pgrp_…`). Folders are paths, relative to where you run
the command; leaving them out means the current folder. A folder can be in one live project at a
time. Archiving keeps the project and its history, but its folders count in their repositories'
projects again; `lunos project archive <project> --undo` brings it back.

#### Flags

| Flag                                     | Description                                                   |
| ---------------------------------------- | ------------------------------------------------------------- |
| <nobr><code>{"--json"}</code></nobr>     | Print the project (or the list) as JSON; a refusal as `error` |
| <nobr><code>{"--archived"}</code></nobr> | With `list`: include archived projects                        |
| <nobr><code>{"--empty"}</code></nobr>    | With `create`: create it without any folder                   |

#### delete

Delete sessions for good: their history, subagent sessions and queued prompts. Files in your
projects are never touched, and a Claude Code or Codex session keeps that tool's own history. A
shared session's link is removed first, and with session sync on, the synced copy is deleted too.
Console shares made from a session or its subagents with `lunos share` (or `/share` to your
organisation's console) are revoked first; if one can't be, the session is kept and the reason is
printed. Console shares made before Lunos recorded which session they came from aren't linked to it
and stay live: find them with `lunos share list` and revoke them with `lunos share revoke <id>`.

```bash
opencode session delete <sessionID...>
opencode session delete --archived --older-than 30d --yes
```

It prints what it deleted and what it skipped, and why.

##### Flags

| Flag                                        | Short | Description                                                           |
| ------------------------------------------- | ----- | --------------------------------------------------------------------- |
| <nobr><code>{"--archived"}</code></nobr>    |       | Delete every archived session instead of the ids given                |
| <nobr><code>{"--older-than"}</code></nobr>  |       | With `--archived`: only those last active before this, e.g. `30d`     |
| <nobr><code>{"--project"}</code></nobr>     |       | With `--archived`: only sessions of the project at this path          |
| <nobr><code>{"--stop"}</code></nobr>        |       | Stop running or waiting sessions first (otherwise they are skipped)   |
| <nobr><code>{"--keep-cloud"}</code></nobr>  |       | Keep the synced copies on Lunos Cloud                                 |
| <nobr><code>{"--keep-shares"}</code></nobr> |       | Leave the console shares made from them live instead of revoking them |
| <nobr><code>{"--yes"}</code></nobr>         | `-y`  | Don't ask for confirmation (needed with `--archived` in a script)     |

### memory

Review long-term memory (see [Rules: long-term memory](/docs/rules#long-term-memory)). `list`, `show` and `export --format markdown` read what is stored without starting memory. A bundle export starts memory to read the graph, unless you pass `--no-graph`.

```bash
opencode memory list [--scope project|user]
opencode memory show <id>
opencode memory search <query>
opencode memory forget <id>
opencode memory purge --scope project|user --yes
opencode memory export [--format bundle|markdown] [--scope project|user|both] [--since <date>]
                       [--out <path>] [--zip] [--encrypt] [--no-graph] [--include-index] [--dir <path>]
opencode memory import <path> [--scope project|user] [--yes] [--dry-run] [--as-facts] [--include-conflicts]
opencode memory migrate --to neo4j [--scope project|user] [--yes] [--include-conflicts]
opencode memory status
opencode memory stats [--scope project|user] [--days N] [--json]
opencode memory setup [--yes] [--project] [--no-check]
opencode memory check [--json]
```

- `export` writes all of memory as a versioned bundle (facts, graph, notes and provenance) to `./lunos-memory-<time>/`, or a `.zip` with `--zip`, or an encrypted `.zip.enc` with `--encrypt`. See [Rules: exporting memory](/docs/rules#exporting-memory).
- `export --format markdown` writes one Markdown file per fact, with its provenance, to `.opencode/memory/export/` (or `--dir`) so you can review memory in git.
- `forget` removes the fact from memory and from that Markdown export folder. Bundles already written are snapshots and keep it.
- `import` reads a bundle, Markdown, or `AGENTS.md` / `CLAUDE.md` / Claude Code memory, verifies and screens every fact, and shows a preview of new, duplicate, conflict and rejected rows. It writes only with `--yes`. See [Rules: importing memory](/docs/rules#importing-memory).
- `purge` deletes a memory's stored facts and graph. Your notes in `.opencode/memory/*.md` are kept.
- `migrate --to neo4j` moves this machine's embedded memory into the external database set in `memory.backend`: it exports a bundle and imports it with the same preview, keeping each fact's id and provenance. It writes only with `--yes`. See [Rules: an external memory database](/docs/rules#an-external-memory-database).
- `status` shows whether memory is on, the backend and whether it can be reached, and each scope's fact count and last write.
- `stats` prints what `/memory`'s Overview and Activity show (see [Rules: memory analytics](/docs/rules#memory-analytics)). `--days` limits growth and recall to the last N days.

  `--json` prints one object, `version: 1`, with these fields:
  - `status`: `on`, `reason`, `backend`, `encryption`, retention, and ledger `health`.
  - `scopes[]`: `counts` (`active`, `outdated`, `expiring`, `expired`, `quarantined`), `lastWrite`, `error`, `chars` and `tokens`.
  - `sources`: counts by `source`, `agent`, `kind`, `native` and `imported`.
  - `growth[]`: per `week` and `scope`, the facts `added`, `outdated`, `forgotten` and `expired`.
  - `recall`: `audit`, `dataSince`, `total`, `perDay[]`, `origin`, `hitRate`, `avgFacts` and `truncatedRate`.
  - `top[]` (`id`, `count`, `last`) and `supersession` (`count`, `chains`).
  - `facts`: each recalled fact's `recalls` and `last`.
  - `groups`: the fact ids behind each count, e.g. `never`, `state:project:outdated`, `source:file`.

- `setup` asks the setup wizard's questions: on or off, where memory is kept, the model, the first-start download, retention and encryption. It then checks memory works and saves to your user config (`--project` for this project). `--yes` accepts every recommended answer. Without a terminal it needs `--yes`. A failed check still saves, but exits with 1.
- `check` remembers a test fact, recalls it and removes it, then says ✓ or the error and how to fix it (`--json` for scripts). The first run downloads the engine and the embedding model.

### settings

View and change settings. With no subcommand it opens the TUI on the [settings screen](/docs/tui#settings-1).

```bash
opencode settings
```

  validates the value against the config schema and refuses keys locked by your organisation, exiting
  non-zero with the reason. Lists take comma-separated values or JSON; structured settings take JSON.

### changelog

Shows what changed in Lunos, from the release notes built into this version, so it works offline.

```bash
lunos changelog [--since <version>] [--full] [--json]
```

Without options it summarizes the version you have. `--since 1.18.43` covers every version after
1.18.43, skipped ones included. The summary lists behaviour changes and security entries first, then
what's new and a count of fixes, one line each with its ticket. `--full` prints the notes as written,
and `--json` prints the entries as `{ version, section, text, tickets }` for scripts. A version with
no notes says `No notes for X.Y.Z.`

### update

Updates Lunos to the latest version or a specific version. `lunos upgrade` is an alias and still works.

```bash
lunos update [target]
```

To update to the latest version.

```bash
lunos update
```

When you're already on the latest version, this prints `Lunos is up to date (X.Y.Z).` and exits 0.

To update to a specific version.

```bash
lunos update v0.1.48
```

While it runs, a spinner shows the step and the elapsed time: checking for the latest version,
downloading and installing `lunos-ai`, then verifying the installed version. If a step takes longer
than a minute, the line adds that the package manager is still working; there's no timeout. With
`NO_COLOR` or `TERM=dumb` you get one `Updating… (step)` line per step instead of the spinner, and
when the output isn't a terminal (a pipe, CI) one plain line per step with no escape codes.

Ctrl+C cancels while Lunos is still checking for the version. Once the package manager is installing
it runs to the end, even if you press Ctrl+C or close the TUI, because stopping it halfway could leave
no working `lunos`.

After a successful update, Lunos prints what changed since the version you had (the same summary
as `lunos changelog --since <your version>`) before the restart hint.

If the update fails, Lunos prints the command to run by hand and exits with code 1. For npm installs
that's `npm i -g lunos-ai@<version> --allow-scripts=lunos-ai`.

A running TUI keeps using the old version until it restarts. After `/update` in the TUI, run
`/restart`: it starts the newly installed version back in the same session. See
[`/restart`](/docs/tui#restart).

#### New version notice

Every time Lunos starts it asks the npm registry (`lunos-ai`, or the registry in your `.npmrc`) for
the latest version. The check runs in the background, never delays startup, and gives up after 3
seconds; if it fails, the last known result is used.

- In the TUI, the bottom-right corner shows `There is a new version: X.Y.Z — please run lunos update`
  on every screen until you update (`New version: X.Y.Z · lunos update` below 100 columns).
- Plain commands such as `lunos models` print `There is a new version: X.Y.Z — please run "lunos update"`
  to stderr, at most once a day. It never goes to stdout, so piped output stays clean.

No check is made, and no notice shown, with `"autoupdate": false`, `LUNOS_DISABLE_AUTOUPDATE=1`,
`LUNOS_OFFLINE=1`, or when an organisation policy sets `"autoupdate": false`.
