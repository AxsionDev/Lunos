title: Rules
description: Set custom instructions for opencode.
---

You can provide custom instructions to opencode by creating an `AGENTS.md` file. This is similar to Cursor's rules. It contains instructions that will be included in the LLM's context to customize its behavior for your specific project.

---

## Initialize

To create a new `AGENTS.md` file, you can run the `/init` command in opencode.

:::tip
You should commit your project's `AGENTS.md` file to Git.
:::

`/init` scans the important files in your repo, may ask a couple of targeted questions when the codebase cannot answer them, and then creates or updates `AGENTS.md` with concise project-specific guidance.

It focuses on the things future agent sessions are most likely to need:

- build, lint, and test commands
- command order and focused verification steps when they matter
- architecture and repo structure that are not obvious from filenames alone
- project-specific conventions, setup quirks, and operational gotchas
- references to existing instruction sources like Cursor or Copilot rules

If you already have an `AGENTS.md`, `/init` will improve it in place instead of blindly replacing it.

---

## Example

You can also just create this file manually. Here's an example of some things you can put into an `AGENTS.md` file.

```markdown title="AGENTS.md"
# SST v3 Monorepo Project

This is an SST v3 monorepo with TypeScript. The project uses bun workspaces for package management.

## Project Structure

- `packages/` - Contains all workspace packages (functions, core, web, etc.)
- `infra/` - Infrastructure definitions split by service (storage.ts, api.ts, web.ts)
- `sst.config.ts` - Main SST configuration with dynamic imports

## Code Standards

- Use TypeScript with strict mode enabled
- Shared code goes in `packages/core/` with proper exports configuration
- Functions go in `packages/functions/`
- Infrastructure should be split into logical files in `infra/`

## Monorepo Conventions

- Import shared modules using workspace names: `@my-app/core/example`
```

We are adding project-specific instructions here and this will be shared across your team.

## Types

opencode also supports reading the `AGENTS.md` file from multiple locations. And this serves different purposes.

### Project

Place an `AGENTS.md` in your project root for project-specific rules. These only apply when you are working in this directory or its sub-directories.

### Global

You can also have global rules in a `~/.config/opencode/AGENTS.md` file. This gets applied across all opencode sessions.

Since this isn't committed to Git or shared with your team, we recommend using this to specify any personal rules that the LLM should follow.

### Claude Code Compatibility

For users migrating from Claude Code, Lunos supports Claude Code's file conventions as fallbacks:

- **Project rules**: `CLAUDE.md` in your project directory (used if no `AGENTS.md` exists)
- **Global rules**: `~/.claude/CLAUDE.md` (used if no `~/.config/opencode/AGENTS.md` exists)
- **Skills**: `~/.claude/skills/` — see [Agent Skills](/docs/skills/) for details

To disable Claude Code compatibility, set one of these environment variables:

```bash
export OPENCODE_DISABLE_CLAUDE_CODE=1        # Disable all .claude support
export OPENCODE_DISABLE_CLAUDE_CODE_PROMPT=1 # Disable only ~/.claude/CLAUDE.md
export OPENCODE_DISABLE_CLAUDE_CODE_SKILLS=1 # Disable only .claude/skills
```

## Precedence

When opencode starts, it looks for rule files in this order:

1. **Local files** by traversing up from the current directory (`AGENTS.md`, `CLAUDE.md`)
2. **Global file** at `~/.config/opencode/AGENTS.md`
3. **Claude Code file** at `~/.claude/CLAUDE.md` (unless disabled)

The first matching file wins in each category. For example, if you have both `AGENTS.md` and `CLAUDE.md`, only `AGENTS.md` is used. Similarly, `~/.config/opencode/AGENTS.md` takes precedence over `~/.claude/CLAUDE.md`.

## Custom Instructions

You can specify custom instruction files in your `opencode.json` or the global `~/.config/opencode/opencode.json`. This allows you and your team to reuse existing rules rather than having to duplicate them to AGENTS.md.

Example:

```json title="opencode.json"
{
  "$schema": "https://opencode.ai/config.json",
  "instructions": ["CONTRIBUTING.md", "docs/guidelines.md", ".cursor/rules/*.md"]
}
```

You can also use remote URLs to load instructions from the web.

```json title="opencode.json"
{
  "$schema": "https://opencode.ai/config.json",
  "instructions": ["https://raw.githubusercontent.com/my-org/shared-rules/main/style.md"]
}
```

Remote instructions are fetched with a 5 second timeout.

All instruction files are combined with your `AGENTS.md` files.

## Keeping durable notes

To keep facts that should carry across sessions, such as "deploys go out on Tuesdays" or "the billing service owns the invoices table", write them as small Markdown files and load them with `instructions`:

```json title="opencode.json"
{
  "instructions": [".opencode/memory/*.md"]
}
```

- Keep one fact per file, so each can be reviewed and deleted on its own.
- Project notes live in the repo and are reviewed like any other change. Personal notes can live in `~/.config/opencode/memory/`, loaded from your global config.
- These files load alongside `AGENTS.md` and don't compete with it.
- Don't put secrets in them: their contents are sent to your model provider as part of the prompt.

### Long-term memory

Lunos can also keep a knowledge graph of what it learns, and recall the relevant parts in later sessions. It is **off unless you turn it on**:

```json title="opencode.json"
{
  "memory": {
    "enabled": true,
    "scope": ["project"],
    "model": "small",
    "embedding": "local",
    "retrieval": { "max_tokens": 1500 },
    "limits": { "max_facts": 5000, "max_fact_chars": 2000 },
    "retention": { "days": 180, "grace_days": 7 },
    "encryption": "off"
  }
}
```

**What you need:** [uv](https://docs.astral.sh/uv/) and Python 3.10–3.13. Memory runs [Cognee](https://github.com/topoteretes/cognee) (Apache-2.0) in a local Python process. Lunos never installs Python for you: without it, memory stays off and says why.

- **Remembering.** The agent saves facts with a `memory_remember` tool. You approve each one: the tool asks by default. It refuses:
  - anything in a turn that used `webfetch`, `websearch`, an MCP resource, or read a file outside the project
  - anything that looks like a key, token or password
  - anything shaped like instructions to the model: "ignore all previous instructions", chat role markers, tool-call syntax
- **Recalling.** Relevant facts are added to your message in a `<memory>` block, each with where and when it was learned, capped at `retrieval.max_tokens`. The agent can also look things up with `memory_search`.
- **Your notes.** Paragraphs in `.opencode/memory/*.md` are part of project memory, with no approval needed. When you edit or delete one, memory follows.
  - The agent's file edits in `.opencode/memory/` ask first, and edits to the stored graph are refused by default. This stops the agent from writing memory through a file instead of the tool.
  - Shell commands can still write files, so review changes to that folder like any other change.
- **Which model.** `memory.model` picks the model that extracts facts and relationships: `"small"` (your `small_model`, the default), `"inherit"` (the main model) or `"provider/model"`. It runs through your normal provider setup and data-residency policy. If the policy denies it, memory doesn't start and the error names `memory.model`.
- **Embeddings** are computed locally (`"local"`). The embedding model (about 87 MB) is downloaded once, from Hugging Face.
- **Where it's stored.**
  - Project memory: `.opencode/memory/graph/`, which is never committed. Lunos writes a `.gitignore` there.
  - `"user"` scope: in the Lunos data directory.
- **Reviewing it.**
  - In the TUI, `/memory` opens a browser: every fact with where it came from, the entities and relationships around the highlighted fact, `ctrl+d` twice to forget it, `ctrl+s` to export and `ctrl+o` to import.
  - `lunos memory list`, `show <id>` and `search <query>` show what is stored and where each fact came from.
  - `lunos memory export` writes all of memory as one bundle (see [Exporting memory](#exporting-memory)). `--format markdown` writes one Markdown file per fact instead, for review in git.
  - `lunos memory import <path>` brings memory in (see [Importing memory](#importing-memory)).
  - `lunos memory forget <id>` removes a fact. `lunos memory purge --scope project --yes` deletes the whole memory.
  - `lunos memory outdate <id> [--by <new id>]` marks a fact as no longer true (see [Facts that stop being true](#facts-that-stop-being-true)). `ctrl+u` twice does the same in the TUI browser.
  - `lunos memory status` shows how many facts are active, outdated, expired and quarantined, and `lunos memory verify` re-checks the ledger (see [Integrity, expiry and encryption](#integrity-expiry-and-encryption)).
- **Turning it off:**
  - `"memory": { "enabled": false }`, or remove the key
  - `LUNOS_DISABLE_MEMORY=1`, which overrides config
  - `/memory off` for the current session
  - `"permission": { "memory": "deny" }`, for all agents or one agent

  When memory is off, no memory process starts, no memory files are created and the memory tools aren't offered.

#### Facts that stop being true

A fact can be marked **outdated**, optionally with the fact that replaces it. It is kept, with when it became true (`valid_from`) and when it stopped (`invalid_at`), but it is no longer recalled. `lunos memory search --history`, or `memory_search` with `history: true`, shows outdated facts too, marked as such. `lunos memory show <id>` shows an outdated fact's `invalid_at` and `replaced_by`.

- **When the agent remembers something that contradicts a fact** (the same subject with a different value, like "billing owns invoices" and then "ledger-service owns invoices"), the approval prompt shows both. If you allow it, you're asked whether to **replace** the old fact (it becomes outdated) or keep both. The agent can also propose a replacement itself (`replaces`), and you're asked the same way. Where no one can answer (`lunos run`), both are kept, and the tool's answer says how to outdate the old one.
- **Observed or inferred.** Each fact the agent saves records whether you said it or it read it in a file (`observed`) or the agent concluded it (`inferred`). Recall labels inferred facts as such. Facts from your notes are observed.

#### Integrity, expiry and encryption

- **Expiry.** `memory.retention.days` makes facts expire that many days after they were saved (by default they never do). A fact can also have its own expiry date. An expired fact is no longer recalled, and is deleted `retention.grace_days` later (default 7), the next time memory starts; the audit log records the deletion. `lunos memory list --expiring [days]` shows what expires within that many days (default 7), and what has expired but not yet been deleted. Facts from your notes never expire: the note is their source.
- **Integrity.** Every line of the ledger (`facts.jsonl`, the record of each fact and where it came from) carries a SHA-256 of its content and provenance, and the lines form a hash chain. If a line doesn't match (it was edited, damaged, removed or moved), that fact is **quarantined**: it is not recalled or exported, and `lunos memory status` and `lunos memory verify` list it with the reason. Forget it with `lunos memory forget <id>`, or, once you have checked it, accept the ledger as it is with `lunos memory verify --reseal --scope <scope>`. These are plain hashes with no secret: they catch damage and hand edits, not someone who rewrites the file and recomputes them.
- **Encryption at rest.** `"encryption": "os-keychain"` encrypts the ledger, line by line (AES-256-GCM), with a random key kept in your OS keychain: macOS Keychain, Windows Credential Manager, or libsecret on Linux. The key is never written to config or to disk. What it covers, and what it doesn't:
  - **Encrypted:** the ledger, in project and user memory.
  - **Not encrypted:** the memory engine's own database files next to it (measured: Cognee's SQLite database, its Kuzu graph file, its LanceDB vector tables, its plain-text copy of each fact under `data/`, and its logs under `logs/` all hold fact text), and your notes in `.opencode/memory/*.md`, which are meant to be read and reviewed in git. Use full-disk encryption (FileVault, BitLocker, LUKS) for those.
  - **If the key is lost**, the ledger can't be read, and nothing else holds it. Lunos refuses to read or write that memory, and says which keychain entry is missing, instead of starting empty; it never makes a new key while an encrypted ledger exists. Restore the keychain entry (from your keychain's backup), or delete that memory with `lunos memory purge`. Export a bundle if you need a copy that doesn't depend on the key.
  - Turning it on encrypts the existing ledger the next time memory starts; turning it off decrypts it (the key must still be there).
- **Audit.** With the [audit log](https://github.com/AxsionDev/Lunos/blob/dev/docs/audit-log.md) on, every memory operation is recorded (`memory.remember`, `recall`, `forget`, `outdate`, `import`, `export`, `purge`, `verify_failed`), with its time, scope, fact ids, counts and where it came from, never a fact's text or a search query, and forwarded to your SIEM like every other event.

#### Exporting memory

`lunos memory export` writes everything in memory to a versioned bundle, format `lunos-memory/1`. Use it for backups, to move memory to another machine or engine, to hand it to someone to review, or for a GDPR data-portability request.

```bash
lunos memory export                              # a folder: ./lunos-memory-<time>/
lunos memory export --zip                        # one .zip file
lunos memory export --encrypt                    # a .zip.enc, locked with a passphrase you're asked for
lunos memory export --scope project --since 2026-09-01 --out backup/
lunos memory export --format markdown            # one Markdown file per fact, as before
```

A bundle holds:

- `facts.jsonl`: every fact, with its provenance (session, agent, source and date), scope, status (active or outdated, with `invalid_at` and `replaced_by`), expiry date if it has one and, where known, whether it was observed or inferred. **The facts are the source of truth.** Quarantined facts are left out, and the manifest counts them.
- `graph.json`: the entities and relationships memory extracted, each listing the ids of the facts it came from.
- `notes/`: copies of your notes in `.opencode/memory/*.md`.
- `manifest.json`: the format and Lunos version, scopes, counts, creation time, and the SHA-256 of every file.
- `SCHEMA.md`: the format, with its JSON Schema, so other tools can read a bundle without Lunos.

What to know:

- **Embeddings and the engine's database files are left out.** They are specific to the model and engine, and are rebuilt when memory is imported. `--include-index` adds them, for a restore into the same engine version and embedding model, which the manifest records. Those files hold every fact's text, so `--include-index` can't be combined with `--since`.
- **Where it goes.** The CLI writes to the folder you run it in unless you pass `--out`. The TUI writes to `memory/exports/` in the Lunos data directory, so a bundle never lands in your project.
- **Reading the graph starts memory**, so memory must be on. With memory off, the export stops and says so; `--no-graph` exports the facts and notes without starting anything.
- **Secrets are checked again.** The export runs the same check as writes do. If anything looks like a key, token or password, nothing is written and the offending ids are listed.
- **Encryption** uses OpenSSL's format (AES-256-CBC, key from PBKDF2-SHA256 with 600,000 iterations). The passphrase is never stored; set `LUNOS_MEMORY_PASSPHRASE` to export without a prompt. Decrypt without Lunos with:

  ```bash
  openssl enc -d -aes-256-cbc -md sha256 -pbkdf2 -iter 600000 -in lunos-memory.zip.enc -out lunos-memory.zip
  ```

  Then check the SHA-256s in `manifest.json`: this mode doesn't detect tampering by itself.

- **A bundle is a snapshot.** Forgetting a fact later doesn't remove it from bundles you have already written. A bundle can hold user memory too, so keep it out of git.
- In the TUI, `ctrl+s` in the `/memory` browser offers the same choices. The passphrase is typed into a plain prompt, as API keys are.

#### Importing memory

`lunos memory import <path>` brings memory in: to restore a backup, to move memory between machines or teammates, or to bring in what you already wrote for other coding agents.

```bash
lunos memory import lunos-memory-20260929-101500.zip.enc    # preview only: nothing is written
lunos memory import lunos-memory-20260929-101500.zip.enc --yes
lunos memory import AGENTS.md --yes                         # becomes a note in .opencode/memory/
lunos memory import ~/.claude/projects/<project>/memory --yes
lunos memory import notes/ --as-facts --scope user --yes
```

It reads:

- **A Lunos bundle**, as a folder, `.zip` or `.zip.enc` (the passphrase is asked for, or read from `LUNOS_MEMORY_PASSPHRASE`). Facts keep their original provenance, and notes come back as notes.
- **Markdown**: a file or a folder. One fact per top-level `- ` bullet, or one per file. The `--format markdown` export reads back with its provenance.
- **Other agents' files**: `AGENTS.md`, `CLAUDE.md` and Claude Code's auto-memory notes come in as notes in `.opencode/memory/` (as `agents-md.md`, `claude-md.md`, and so on, never under their own names, which other tools load as instructions). `--as-facts` imports them as facts instead.

**Imported memory is untrusted.** A checksum or a passphrase proves where a bundle came from, not that what it says is safe. So an import:

1. **Checks the format.** A bundle from a newer major version is refused.
2. **Verifies the bundle.** Every file's SHA-256 is checked, after decrypting. One changed byte, a missing file or a file the manifest doesn't list refuses the whole bundle.
3. **Screens every fact and note paragraph** with the checks agent writes pass: the size limit, the secret check, and the check for instruction-shaped text.
4. **Dedupes** against what memory holds, and flags near-duplicates.
5. **Finds conflicts**: the same subject with a different value is shown next to the fact it contradicts.
6. **Previews.** A table shows every row as new, duplicate, conflict or rejected, with the reason. Nothing is written without `--yes`, or approval in the TUI. `--dry-run` previews even with `--yes`.
7. **Stores** the new rows. `--include-conflicts` also writes conflicts and near-duplicates. Each imported fact's source becomes `import:<file>#<sha256>`, its original provenance is kept as its origin, and it is marked imported.

What to know:

- **The graph and the index are never imported.** Memory re-extracts entities and relationships from the facts, and re-embeds them with your configured, local embedding model. `graph.json` and `index/` files in a bundle are ignored.
- **Lifecycle is kept.** Outdated facts come in outdated (history, never recalled), linked to their replacement when it comes in too; expiry dates and observed/inferred are kept; a fact that has already expired is rejected.
- **Recall labels imported facts** "imported", with where they came from, inside the `<memory>` block that is always reference, never instructions.
- **Where facts go.** A bundle's facts go back to their own scope. Markdown goes to project memory. `--scope project|user` puts everything in one memory. Notes are always project memory.
- **Limits.** If the import would pass `memory.limits.max_facts`, it stops at the preview.
- **Models.** Extracting each fact's graph is one call to your `memory.model`, and the preview says how many. Both `memory.model` and `memory.embedding` are checked against your data-residency policy before anything is read. A denied model stops the import, and the error names the setting.
- **The audit log** records each import: the counts and the SHA-256 of what was read, never the text.
- In the TUI, `ctrl+o` in the `/memory` browser asks for the path and shows the preview. New rows start approved; `enter` approves or rejects one row, `ctrl+a` all of them, and `ctrl+s` imports.

## Referencing External Files

While opencode doesn't automatically parse file references in `AGENTS.md`, you can achieve similar functionality in two ways:

### Using opencode.json

The recommended approach is to use the `instructions` field in `opencode.json`:

```json title="opencode.json"
{
  "$schema": "https://opencode.ai/config.json",
  "instructions": ["docs/development-standards.md", "test/testing-guidelines.md", "packages/*/AGENTS.md"]
}
```

### Manual Instructions in AGENTS.md

You can teach opencode to read external files by providing explicit instructions in your `AGENTS.md`. Here's a practical example:

```markdown title="AGENTS.md"
# TypeScript Project Rules

## External File Loading

CRITICAL: When you encounter a file reference (e.g., @rules/general.md), use your Read tool to load it on a need-to-know basis. They're relevant to the SPECIFIC task at hand.

Instructions:

- Do NOT preemptively load all references - use lazy loading based on actual need
- When loaded, treat content as mandatory instructions that override defaults
- Follow references recursively when needed

## Development Guidelines

For TypeScript code style and best practices: @docs/typescript-guidelines.md
For React component architecture and hooks patterns: @docs/react-patterns.md
For REST API design and error handling: @docs/api-standards.md
For testing strategies and coverage requirements: @test/testing-guidelines.md

## General Guidelines

Read the following file immediately as it's relevant to all workflows: @rules/general-guidelines.md.
```

This approach allows you to:

- Create modular, reusable rule files
- Share rules across projects via symlinks or git submodules
- Keep AGENTS.md concise while referencing detailed guidelines
- Ensure opencode loads files only when needed for the specific task

:::tip
For monorepos or projects with shared standards, using `opencode.json` with glob patterns (like `packages/*/AGENTS.md`) is more maintainable than manual instructions.
:::
